    GoVector CGO/SWIG 隔离架构设计¶

    📐 架构设计原则¶

    核心目标¶

    ✅ 保持 core 包的纯度 - 无任何 CGO 依赖
    ✅ 添加 SWIG 支持 - 通过独立适配层
    ✅ 单向依赖 - 适配层依赖核心层，不能反向依赖
    ✅ 构建隔离 - 可以选择性构建 CGO 组件

    🏗️ 目录结构¶

    govector/
│
├── core/                          # ✅ 纯净核心包（无 CGO）
│   ├── collection.go              #    纯 Go 实现
│   ├── storage.go                 #    纯 Go 实现
│   ├── models.go                  #    纯 Go 实现
│   ├── index.go                   #    纯 Go 实现
│   └── ...                        #    其他核心模块
│
├── capi/                          # ✅ CGO/SWIG 适配层
│   ├── govector_c.h               #    C 头文件（API 声明）
│   ├── govector_c.go              #    Go 导出实现（import "C"）
│   ├── govector.i                 #    SWIG 接口文件
│   ├── doc.go                     #    包说明
│   ├── README.md                  #    使用说明
│   ├── Makefile                   #    构建配置
│   ├── build.sh                   #    构建脚本
│   └── examples/                  #    使用示例
│       ├── demo.py                #    Python 演示
│       └── cpp_example.cpp        #    C++ 示例
│
├── api/                           # ✅ HTTP API 层（可选，无 CGO）
│   └── server.go                  #    RESTful API
│
└── cmd/
    └── govector/                  # ✅ CLI 入口
        └── main.go

    🔑 关键设计决策¶

    1. 包的职责分离¶

    包名 职责 CGO 依赖 可独立发布
    core 核心业务逻辑 ❌ 无 ✅ 是
    capi CGO/SWIG 适配 ✅ 有 ✅ 是
    api HTTP API ❌ 无 ✅ 是

    2. 依赖关系¶

    ┌─────────────┐
│   External  │  (Python, C++, Java, etc.)
└──────┬──────┘
       │
       ▼
┌─────────────┐
│    capi     │  (CGO/SWIG Adapter)
└──────┬──────┘
       │ calls
       ▼
┌─────────────┐
│    core     │  (Pure Go Logic)
└─────────────┘

    关键规则： - ✅ capi 可以 import core - ❌ core 不能 import capi - ❌ core 中不能有任何 import "C"

    3. 构建隔离¶

    # 只构建纯 Go 核心库
go build ./core          # ✅ 成功，无需 CGO

# 只构建 HTTP API
go build ./api           # ✅ 成功，无需 CGO

# 构建 CGO 适配层（需要 SWIG）
cd capi && ./build.sh    # ✅ 需要 CGO 环境

# 完整构建（包含所有组件）
go build ./...           # ✅ 全部构建

    💻 实现细节¶

    core 包 - 保持纯净¶

    core/collection.go 示例： 

    package core

import (
    "fmt"
    "sync"
    "time"
)

// ✅ 纯 Go 实现，无任何 CGO
type Collection struct {
    Name      string
    VectorLen int
    Metric    Distance
    // ...
}

func (c *Collection) Upsert(points []PointStruct) error {
    // 纯 Go 逻辑
    return nil
}

    检查清单： - [x] 没有 import "C" - [x] 没有使用 unsafe.Pointer 进行 CGO 操作 - [x] 所有类型都是纯 Go 类型 - [x] 可以独立编译和测试

    capi 包 - CGO 适配器¶

    capi/govector_c.go 示例： 

    package capi

/*
#include "govector_c.h"
#include <stdlib.h>
*/
import "C"

import (
    "encoding/json"
    "unsafe"

    // ✅ 导入核心包
    "github.com/DotNetAge/govector/core"
)

//export govector_collection_create
func govector_collection_create(
    name *C.char,
    vectorDim C.int,
    metric C.DistanceType,
    // ...
) C.CollectionHandle {
    // ✅ 调用核心包的功能
    col, err := core.NewCollectionWithParams(
        C.GoString(name),
        int(vectorDim),
        toDistance(metric),
        store,
        bool(useHnsw),
        params,
    )

    if err != nil {
        return nil
    }

    // 返回句柄给 C 代码
    return createHandle(col)
}

// 辅助函数：转换 C 类型为 Go 类型
func toDistance(metric C.DistanceType) core.Distance {
    switch metric {
    case C.DISTANCE_COSINE:
        return core.Cosine
    case C.DISTANCE_EUCLID:
        return core.Euclid
    default:
        return core.Cosine
    }
}

    关键特点： - ✅ 只有 capi 包包含 import "C" - ✅ 通过适配函数转换 C 和 Go 类型 - ✅ 调用 core 包的核心逻辑 - ✅ 不修改 core 包的任何代码

    🚀 构建流程¶

    1. 构建纯 Go 核心库（无需 CGO）¶

    # 构建 core 包
go build ./core

# 构建 API 服务
go build ./api

# 构建 CLI
go build ./cmd/govector

    2. 构建 CGO/SWIG 组件（需要 CGO 环境）¶

    cd capi

# 步骤 1: 生成 SWIG 包装文件
swig -cgo -python -py3 -o govector_wrap.cxx govector.i

# 步骤 2: 构建 Go 静态库
go build -buildmode=c-archive -o libgovector_c.a .

# 步骤 3: 编译 Python 模块
g++ -fPIC -shared govector_wrap.cxx -o _govector.so \
    $(python3-config --includes) \
    -L. -lgovector_c

    3. 条件编译（可选）¶

    如果希望在某些场景下完全排除 CGO，可以使用构建标签：

    capi/govector_c_nocgo.go: 

    // +build !cgo

package capi

// 当禁用 CGO 时提供空实现或错误提示
func init() {
    panic("CGO support is not enabled")
}

    capi/govector_c.go: 

    // +build cgo

package capi

/*
#include "govector_c.h"
*/
import "C"

// ... CGO 实现

    使用方式： 

    # 构建带 CGO 的版本
go build -tags cgo ./capi

# 构建纯 Go 版本（不含 CGO）
go build -tags !cgo ./...

    📦 发布策略¶

    方案 A: 统一发布（推荐）¶

    在同一个仓库中包含所有内容：

    govector/
├── core/              # 纯 Go 核心
├── capi/              # CGO/SWIG 适配
├── api/               # HTTP API
└── go.mod             # Go 模块定义

    优点： - ✅ 用户可以根据需要选择使用哪些组件 - ✅ 核心包保持纯净 - ✅ 方便维护版本一致性

    发布命令： 

    # 发布整个模块
git tag v0.2.0
git push origin v0.2.0

    方案 B: 分离发布¶

    将 capi 作为独立的子模块：

    # 主仓库
govector/
├── core/
├── api/
└── go.mod

# 独立仓库
govector-capi/
├── govector_c.h
├── govector_c.go
├── govector.i
└── go.mod  # 依赖 govector

    govector-capi/go.mod: 

    module github.com/DotNetAge/govector-capi

go 1.25.1

require github.com/DotNetAge/govector v0.2.0

    优点： - ✅ 完全隔离 CGO 代码 - ✅ 可以独立版本化 - ✅ 用户可以按需安装

    缺点： - ❌ 增加维护复杂度 - ❌ 需要管理两个仓库的版本同步

    ⚠️ 常见陷阱与避免方法¶

    陷阱 1: 在 core 包中意外引入 CGO¶

    ❌ 错误示例： 

    // core/collection.go
package core

import "C"  // ❌ 错误！污染了核心包

type Collection struct {
    // ...
}

    ✅ 正确做法： 

    // core/collection.go
package core

// ✅ 纯 Go，无 import "C"

type Collection struct {
    // ...
}

// capi/govector_c.go
package capi

import "C"  // ✅ 只在适配层使用
import "github.com/DotNetAge/govector/core"

    陷阱 2: 循环依赖¶

    ❌ 错误： 

    // core/storage.go
package core

import "github.com/DotNetAge/govector/capi"  // ❌ 循环依赖！

    ✅ 正确： 

    // core/storage.go
package core

// ✅ 无外部依赖

// capi/govector_c.go
package capi

import "github.com/DotNetAge/govector/core"  // ✅ 单向依赖

    陷阱 3: 类型泄漏¶

    ❌ 错误： 

    // core/models.go
package core

import "C"  // ❌ C 类型泄漏到核心包

type PointStruct struct {
    ID     string
    Vector *C.float  // ❌ 使用了 C 类型
}

    ✅ 正确： 

    // core/models.go
package core

type PointStruct struct {
    ID     string
    Vector []float32  // ✅ 纯 Go 类型
}

// capi/govector_c.go
package capi

func convertPoint(cPoint *C.PointStruct) core.PointStruct {
    // ✅ 在适配层进行类型转换
    return core.PointStruct{
        ID: C.GoString(cPoint.id),
        Vector: cFloatSliceToGo(cPoint.vector, cPoint.dim),
    }
}

    📊 性能对比¶

    直接调用 vs CGO 调用¶

    调用方式 延迟 吞吐量 适用场景
    core 直接调用 1x 1x Go 应用内部
    capi CGO 调用 10-100x 0.1-0.5x 跨语言边界
    HTTP API 100-1000x 0.01-0.1x 远程服务

    优化建议¶

    1. 批量操作减少调用次数 

      // ✅ 好：批量插入
Upsert(points_batch)

// ❌ 差：单个插入
for p in points:
    Upsert([p])

    2. 优先使用纯 Go 接口 

      // Go 应用：直接使用 core 包
import "github.com/DotNetAge/govector/core"

// Python/C++ 应用：使用 capi
import govector

    🎯 最佳实践总结¶

    ✅ 必做清单¶

    1. 保持 core 包纯净
    2. [x] 无任何 import "C"
    3. [x] 无 C 类型混用

    4. [x] 可独立编译测试

    5. capi 包作为专用适配层

    6. [x] 所有 CGO 代码集中在此
    7. [x] 负责类型转换

    8. [x] 调用 core 包功能

    9. 严格的单向依赖

    10. [x] capi → core（允许）

    11. [x] core → capi（禁止）

    12. 清晰的文档说明

    13. [x] 说明架构设计
    14. [x] 提供使用示例
    15. [x] 标注 CGO 依赖

    ❌ 禁止清单¶

    • [ ] 不要在 core 包中使用 CGO
    • [ ] 不要让 core 包依赖 capi
    • [ ] 不要在核心逻辑中混用 C 类型
    • [ ] 不要隐藏 CGO 依赖（明确标注）

    📝 迁移指南¶

    如果已有 CGO 代码污染了 core 包¶

    步骤 1: 识别 CGO 代码 

    # 查找所有使用 import "C" 的文件
grep -r 'import "C"' core/

    步骤 2: 迁移到 capi 

    # 移动文件
mv core/cgo_wrapper.go capi/govector_c.go

# 修改 package 声明
# core/cgo_wrapper.go: package core ❌
# capi/govector_c.go:   package capi ✅

# 更新导入
# import "C" ✅ (只在 capi 中)

    步骤 3: 清理 core 包 

    // 删除 core 包中的 import "C"
// 替换 C 类型为 Go 类型
// 确保所有测试通过

    🎉 总结¶

    通过本架构设计，我们实现了：

    ✅ 保持 core 包纯度 - 无任何 CGO 污染
    ✅ 添加 SWIG 支持 - 通过独立适配层
    ✅ 清晰的职责分离 - core 负责逻辑，capi 负责适配
    ✅ 灵活的构建选项 - 可选择性构建 CGO 组件
    ✅ 易于维护 - 单向依赖，无循环依赖

    这种设计既满足了跨语言集成的需求，又保持了核心代码的纯洁性和可维护性。
